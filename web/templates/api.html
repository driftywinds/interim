Overview

Base URL: {{.APIBase}}

Retention: {{.RetentionLabel}} per file. Per-file limit: {{.MaxFileSize}}. Signed download lifetime: {{.DownloadTTL}}.

A single-PUT upload follows three steps:

  1. POST /uploads creates an upload intent, reserves storage, and returns a short-lived presigned PUT URL.
  2. Your client PUTs the raw bytes to that URL. No file bytes pass through interim.
  3. POST /uploads/{id}/complete verifies the object in storage and creates the public file record.

If the instance has multipart uploads enabled and the file is above the configured threshold, POST /uploads returns mode: "multipart" instead. The client requests part URLs, uploads each part, reports its ETag, then completes. Parts can be retried individually and resumed from GET /uploads/{id}.

A pending upload can be canceled with DELETE /uploads/{id}. Unclaimed intents and their temporary objects are removed by a janitor after the upload window expires.

Authentication

{{if .PublicUploads}}

Create a user hash with POST /keys. It is returned once and can be sent as a bearer credential:

{{else}}

User hashes are issued by the admin, who also marks them approved for uploads. Public creation through POST /keys is disabled. Send your hash as a bearer credential:

{{end}} 
Authorization: Bearer interim_...

X-API-Key: interim_... is also accepted. Creating an upload intent is the only upload step that uses this credential; completion and abort use the separate upload_token, which is valid until the intent expires.

GET /keys/me reports an approved flag. With public uploads disabled, only approved hashes may create upload intents.

Lost user hashes cannot be recovered. Only a SHA-256 hash is stored on the server.

Direct upload contract

The create response contains:

{
  "upload_id": "…",
  "mode": "single",
  "url": "https://storage.example/…signature…",
  "method": "PUT",
  "headers": {
    "Content-Type": "application/pdf",
    "Content-Disposition": "attachment; filename=…"
  },
  "expires_at": "2026-10-25T09:30:00Z",
  "intent_expires_at": "2026-10-25T09:45:00Z",
  "upload_token": "…",
  "complete_url": "{{.APIBase}}/uploads/…/complete",
  "abort_url": "{{.APIBase}}/uploads/…",
  "delete_token": "…"
}

Send the bytes with exactly the returned method, URL, and headers. Do not send a multipart form to the S3 URL. The S3 bucket must allow CORS for your web origin, including the Content-Type and Content-Disposition request headers.

After the PUT succeeds, call complete_url with X-Upload-Token: <upload_token>. The server does a HEAD and accepts the object only when its real size is greater than zero and no larger than the declared size and the configured file cap.

Save delete_token. Anonymous uploads can only be deleted with it. The complete response returns the file record and page URL, not the delete token again.

{{if .MultipartEnabled}}

Multipart mode

The create response includes part_size, part_count, parts_url, and status_url. The upload token is required on all part requests.

POST /uploads/UPLOAD_ID/parts
X-Upload-Token: UPLOAD_TOKEN
{"part_numbers":[1,2,3]}

PUT PART_URL
<part bytes>

PUT /uploads/UPLOAD_ID/parts/1
X-Upload-Token: UPLOAD_TOKEN
{"etag":"\"...\"","size":16777216}

All parts 1–part_count must be recorded before completion. GET /uploads/UPLOAD_ID returns completed_parts so a client can resume. The server verifies provider-side part sizes/ETags, assembles the parts, verifies the final size, and uses the staging key as the live object.

{{end}}

Quickstart

1. Get a user hash

{{if .PublicUploads}} 
curl -X POST {{.BaseURL}}/api/v1/keys \
  -H 'Content-Type: application/json' \
  -d '{"name":"my-cli"}'
{{else}}

Ask the admin to generate a user hash for you in /admin. Public hash creation is disabled on this instance.

{{end}}

2. Create an upload intent

curl -X POST {{.BaseURL}}/api/v1/uploads \
  -H 'Authorization: Bearer interim_...' \
  -H 'Content-Type: application/json' \
  -d '{"name":"sample.bin","size":12345,"content_type":"application/octet-stream"}'

3. PUT the bytes directly to S3

curl -X PUT "SIGNED_URL_FROM_RESPONSE" \
  -H 'Content-Type: application/octet-stream' \
  -H 'Content-Disposition: attachment; filename=sample.bin' \
  --data-binary @sample.bin

4. Complete the upload

curl -X POST "COMPLETE_URL_FROM_RESPONSE" \
  -H 'X-Upload-Token: UPLOAD_TOKEN_FROM_RESPONSE'

The response is {"upload_id":"…","file":{…}}. Use file.page_url for the public download page.

5. Ask for a download link

curl -X POST {{.BaseURL}}/api/v1/files/FILE_ID/download

The returned url is short-lived. Depending on the instance configuration it is either a signed S3 GET URL or a worker-proxied token URL. Do not store it; request a new one when needed.

6. Delete a file

curl -X DELETE {{.BaseURL}}/api/v1/files/FILE_ID \
  -H 'Authorization: Bearer interim_...'

Anonymous uploads are deleted with the per-file token:

curl -X DELETE {{.BaseURL}}/api/v1/files/FILE_ID \
  -H 'X-Delete-Token: DELETE_TOKEN_FROM_INTENT'

Complete an upload POST /uploads/{id}/complete

Requires X-Upload-Token. {{if .MultipartEnabled}}In multipart mode, assembles the reported parts first and uses the staging key as the live object. {{end}}It verifies the object with a HEAD request, checks its actual size, consumes the quota reservation, and commits the file. Single PUTs are copied to a separate live key. This endpoint is idempotent: a retry of an already committed upload returns the existing file.

POST {{.APIBase}}/uploads/UPLOAD_ID/complete
X-Upload-Token: UPLOAD_TOKEN_FROM_INTENT
HTTP/1.1 201 Created
{"upload_id":"…","file":{ … }}

409 upload_missing means the PUT has not reached storage yet. 409 upload_parts_incomplete means not all multipart parts have been reported. 410 upload_expired means the intent window ended and the temporary object was removed.

Abort an upload DELETE /uploads/{id}

Requires X-Upload-Token. Aborts an in-progress multipart upload, deletes any staging object, releases the reservation, and closes the intent. Returns 204; committed uploads return 409.

DELETE {{.APIBase}}/uploads/UPLOAD_ID
X-Upload-Token: UPLOAD_TOKEN_FROM_INTENT

Errors and limits

StatusCodeMeaning
400invalid_request / not_multipart / invalid_part / invalid_etag / invalid_part_sizeMalformed JSON, wrong upload mode, part number, ETag, or part size.
401unauthorized / uploads_restrictedMissing or invalid user hash / upload token, or an anonymous upload while public uploads are off.
403forbidden / upload_not_allowed / key_creation_disabledInvalid delete or upload token, an unapproved hash, or public hash creation while uploads are restricted.
404not_foundUnknown file, upload, or endpoint.
409upload_missing / upload_parts_incompleteThe PUT has not reached storage yet, or not all multipart parts are recorded.
410expired / upload_expiredThe file retention period or upload window has ended.
413file_too_large / part_size_mismatchDeclared or actual object exceeds the file cap, or a provider part does not match its declared size.
429rate_limitedToo many requests; check Retry-After.
507storage_fullNo storage capacity available.

Errors use a single envelope:

{
  "error": {
    "code": "storage_full",
    "message": "Storage maxed out — please try again later.",
    "request_id": "…"
  }
}

Send X-Request-ID in bug reports; the server also returns one on every response. API responses are Cache-Control: no-store.
